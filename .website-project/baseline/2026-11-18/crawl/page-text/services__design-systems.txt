THREE SURFACES Different density, same meaning. Surfaces need different density. They still need one set of status colors, one type scale, and components that behave the same way. 01 · OPERATOR CONSOLE Dense, keyboard-first, long shifts Tables, bulk actions, and queues that stay readable at the end of a shift. 02 · DRIVER APP Large targets, glare, weak signal Big tap targets, strong contrast, and states for when the network drops. 03 · CUSTOMER PORTAL Calm, read-mostly, status first Tracking and documents for people who check in occasionally and need a clear answer. DRIFT What happens without one. 01 · STATUS “At risk” is three different colors Console, app, and portal each invented their own status colors, so the same load looks different depending on who opens it. 02 · STATES Empty, error, and offline were never designed The happy path got components. Exceptions, loading, and permission-denied were drawn once on a screen and never added to the library. 03 · HANDOFF Figma and code disagree Names in the design file do not match variables in the front end, so every sprint re-translates the same decisions. WHAT YOU RECEIVE A kit designers and engineers both open. TOKENS Color, type, spacing, density, and status semantics, named the way your engineers name variables. COMPONENTS A Figma library where each component has its states: default, hover, focus, disabled, error, loading, empty. PATTERNS Tables, bulk selection, filters, forms, and empty and error states, documented where they are used. DOCS AND HANDOFF Usage notes, naming mapped to your front-end variables, and a short rule for how new components get added. Delivered in Figma with written specs. Implementing the components in your codebase is a separate engineering scope. HOW IT STAYS ALIVE Inventory, tokens, components, ownership. 01 · INVENTORY What the live product actually uses We list what exists, what duplicates, and what shipping UI references. You provide: product access, current Figma files, and the front-end framework. 02 · TOKENS Named the way engineering talks Type, color, density, and status first, because everything else inherits from them. 03 · COMPONENTS Built from the surfaces that ship We start with what the live product needs most, not a hundred components in one pass. 04 · OWNERSHIP Someone to maintain it Adoption is a workflow, not a launch email. We agree with you who approves changes and where docs live. SCOPE AND LIMITS What a design system here is not. The system is as useful as the team using it. A few honest limits. Not brand identity. Logo, voice, and positioning belong to branding. Not an accessibility audit. We check contrast on tokens, but we do not certify conformance. Not self-maintaining. It needs an owner on your side, usually a designer or an engineer. Not everything at once. We build what the product uses first and add the rest as surfaces ship.
