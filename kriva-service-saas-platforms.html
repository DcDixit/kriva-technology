The platform

The permission on screen is the one the API enforces.

A multi-tenant product is three layers at once: the data boundary between tenants, the roles inside each tenant, and the screens people use every day. One in-house team designs and engineers all three, so they cannot drift apart.

  • Tenant scoping checked in the API, not only hidden in the UI
  • Roles a customer admin can explain to a new hire
  • An admin console your operators can run without engineering

Where it stalls

The product works.
The tenant does not stick.

Live SaaS rarely fails on polish. It fails when tenant rules, roles, and surfaces drift apart, and nobody can say what a tenant should do next or what it is allowed to see.

01

Tenant boundaries live in the UI

Records are filtered on screen, but the API answers for whatever tenant ID it is given. One missed filter can show one customer another customer's data.

Cost: Security exposure, stalled security reviews

02

Permission fog

Roles were added for sales and security. Users hit “you don’t have access” with no path to the owner or admin who can grant it.

Cost: Blocked actions, support tickets

03

Empty workspace after signup

The happy path assumes an admin who already knows the product. New tenants hit a blank state and leave, or open a ticket that should have been a first-run path.

Cost: Churn before first value

04

Releases hit every tenant

Teams freeze work rather than ship in small steps. Without a shared kit and feature flags, each release risks forking admin and customer into two roadmaps.

Cost: Slower releases, tenant regressions

What we build

The platform under the screens.

The same team that designs the role model writes the code that enforces it. These are the engineering parts we take on in a live multi-tenant product.

01 · Tenant isolation

Data that stays inside its tenant

Every record carries its tenant, and the API checks it on every read and write, so a missed filter on screen cannot expose another customer's data. We agree the isolation model with your engineers before any migration.

02 · Roles and permissions

One model, enforced in the API

Roles defined once, checked server-side, and reflected in the UI. Blocked actions name who can grant access, and role changes are written to an audit log.

03 · APIs and webhooks

Integrations that fail visibly

Node.js or Python APIs on PostgreSQL, with clear errors, idempotent writes, and retry queues, so partner and customer integrations do not drift silently.

04 · SSO and onboarding

Sign-in that reaches the job

SSO sign-in connected to the role model, with a safe default role so a new user completes a real task before anyone configures advanced policy.

05 · Billing and subscriptions

Plans, seats, and the ledger

Plan, seat, and billing screens inside the product. Subscription and payment events from Stripe or your billing system post to QuickBooks Online or Xero, with an exception queue finance can review.

06 · Modernization

New surfaces beside the old ones

New Next.js and React surfaces run beside the current app behind feature flags, tested in staging, and go live in phases once your team signs off.

Freight platform scenario

Three users, one load, three different screens.

An example of the role design we do for logistics software. It is a scenario to scope against your product, not a published case.

01 · Shipper user

Sees their own loads, nothing else

Tracking, documents, and exceptions for loads they booked. No carrier rates, no other shipper's data, and a clear note when something is hidden by design.

02 · Carrier user

Accepts work and submits proof

Tendered loads, POD upload, and invoice status. When an action is blocked, the screen names the dispatcher or admin who can unblock it.

03 · Broker admin

Manages tenants and exceptions

Invites, roles, integrations, and a queue of exceptions across tenants. Everything powerful sits behind clear permissions and an audit trail.

For the dispatch side of the same product, see trucking and logistics solutions and dispatch CRM design. For carrier-facing mobile, see driver and field apps.

How we engage

From tenant map to phased rollout.

Four steps, each tied to your live product. The full process covers how we run projects in general.

    Map tenants and roles

    Who is in each workspace, what they can see and do, and where tenant rules are enforced today. Named before screens or code.

  2. 02

    Design both surfaces

    Admin and customer in one family: empty states, blocked actions, and the path to whoever can grant access.

  3. 03

    Build behind flags

    Permission checks, APIs, and screens shipped in small releases behind feature flags, demoed every week.

  4. 04

    Roll out in phases

    Pilot tenants first, then the rest, in a release order that keeps every workspace usable.
